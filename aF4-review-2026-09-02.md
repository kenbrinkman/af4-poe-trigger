# Full-project review — aF4 PoE trigger, 2026-09-02

**Scope:** every file in the repository read in one pass — all markdown, `af4-feeder.yaml`,
the four Python sources, the KiCad board, the shipped Gerbers and drill file, both
quotation spreadsheets, the board renders, and the public GitHub mirror. Load-bearing
claims were re-derived rather than read.

**Occasion:** rev E went to fabrication today. This is the first review taken after the
design stopped moving, so its job is different from the two before it — `aF4-audit-2026-08-28.md`
attacked rev D looking for defects, `aF4-prefab-review-2026-08-31.md` cleared rev E for
ordering. This one asks what is *left*, now that the board is out of our hands.

---

## Bottom line

**The design is closed and correct. What was left was drift and one security defect, and
both are now fixed. What remains is a flash, two headers and a commissioning pass.**

Nothing found in this pass would change the board, and nothing found would have changed the
decision to pay. The load-bearing engineering has now survived three independent passes and
a bench session. But the project has acquired a **second-order version of its own signature
failure**: where §7 of the master reference catalogues *values asserted rather than checked*,
what remains is **values that were correct when written and were never revisited after their
inputs changed**. Ten open items were closed between 2026-08-28 and 2026-09-01 without the
ledger that tracks them being updated, and the two circuit diagrams still showed a resistor
value that was corrected five days ago.

That is a better class of problem than the one before it. It is still the one to watch,
because it is invisible from inside any single document — every file was internally
consistent.

## Findings

### 1. ✅ FIXED — three secrets were committed to a public repository

`af4-feeder.yaml` carries the API encryption key, the OTA password and — as of 2026-09-01 —
the `web_server` password, all in plaintext, in a repo that is **public on GitHub**.

The 2026-08-28 audit flagged this as "related hygiene" at the end of the web-server finding.
It read as a minor note because the audit described the repo, not its visibility. It is the
only live security defect in the project.

The sharp part is the sequence. `web_server: auth:` was added on 2026-09-01 specifically to
close an unauthenticated LAN control path — and the commit that closed it published the
credential. The hole is the same size it was, moved from the LAN to the internet.

**Fixed the same day.** All three now resolve through `!secret` against a gitignored
`secrets.yaml`, **and all three were rotated** — which is the part that actually
remediates, because removing them from HEAD is not remediation while history keeps the
old values.

History was deliberately **not** rewritten. Rotation makes the exposed values worthless;
a `git-filter-repo` pass would rewrite all 46 commit SHAs and GitHub can still serve
cached objects for some time afterwards, so it would be cosmetic on top of the fix that
matters. Decision recorded rather than left implicit, so nobody re-opens it.

The timing was lucky: because item 11 had never been flashed, the rotation costs nothing.
The one pending OTA now carries GPIO32, the 20 s pulse, the boot lockout, web auth **and**
all three new credentials in a single install. Two consequences are written into
`aF4-assembly-guide.md` §4 at the point of use — the Device Builder needs its own copy of
`secrets.yaml` (`!secret` resolves beside the file being compiled, not against this repo),
and the first install after a rotation authenticates with the **old** OTA password while
installing the new one. Home Assistant will prompt once for the new API key; entity IDs and
history survive because the device name is unchanged.

### 2. ✅ FIXED — the two circuit diagrams showed the defect that was fixed on 2026-08-28

`aF4-wiring-diagram.svg` and `aF4-system-diagram.svg` were both dated 2026-08-27 and had
never been touched since. Between them they asserted:

- **R6 = 10k and R7 = 10k** — the exact shared-value defect that put the green LED at
  ~0.5 mcd and was corrected to 1.0 k / 6.8 k on 2026-08-28;
- "≥9 V held >6 s" — the most permissive of inD's three published hold times, dropped from
  every other document on 2026-09-01;
- "10 s pulse · 290 s lockout" — superseded by 20 s / 290 s;
- "ISOLATION BARRIER — 4.3 mm" — a figure the master reference formally **withdrew**, since
  it described the wrong U1 footprint;
- "rev D" throughout;
- "Commissioning: TP2 must read 10.3–10.5 V" — a band that would fail a good board.

These were the last artifacts in the project stating something known to be false, and the
worst kind: a diagram is what someone reads *first* when rebuilding, and R6/R7 is a value
you would copy without questioning. Both are now corrected, and the wiring diagram gains the
8.3 mA / 1.2 mA annotations that make the deliberate asymmetry legible rather than looking
like a mistake.

### 3. ✅ FIXED — the open-items ledger had fallen ten items behind

Master reference §8 listed items 3, 5, 6, 7, 8, 9, 10 and 13 as open. Every one of them had
been closed between 2026-08-28 and 2026-09-01 — by the bench session, the vendor-documentation
pass, or the firmware edit — and the closure was recorded in the file that did the work but
never propagated back to the ledger.

This matters more than ordinary staleness because §8 is the **checklist that gates go-live**.
A list that over-reports open work gets skimmed, and a skimmed list is how the two genuinely
blocking items (11, firmware not flashed; 12, headers not soldered) get missed among eight
that are already done. The ledger now reads 10 closed / 4 open / 2 informational, and the
commissioning gate carries the widened bands and steps 6.7–6.8.

### 4. The firmware has been ready and unflashed for six days

`af4-feeder.yaml` in the repo is correct and complete: GPIO32, the 20 s pulse, the 310 s
cycle, the flash-persisted boot lockout, web auth, and the nested `clk:` block. **None of it
is on the device.** The unit on the tank is still the GPIO13 build with a 10 s pulse.

This is not a new finding — it has been open item 11 since 2026-08-27 — but it is worth
restating plainly now that everything around it is finished. It is the only thing standing
between the current state and a working system, it takes minutes, and it is entirely
independent of the boards arriving. It also carries the GPIO13 → GPIO32 change, which means
**the hat cannot be plugged in until it is done**.

### 5. Smaller drift, all now corrected

- `README.md` and `aF4-reference.md` still described a 10 s pulse.
- `aF4-vendor-docs-notes.md` §2 said the port's input current "stays open" when the same
  day's bench work had measured it at ~11 kΩ / ~0.95 mA.
- `aF4-enclosure-notes.md` contradicted itself inside one file: the rev C→D change table
  said "two LED sight holes", the layout section said four with light pipes.
- Master reference §6 also still said two, and §4 still tagged DRC as reported-not-re-run
  when the 2026-08-31 review had re-run it independently.
- `aF4-pcb-notes.md` still carried the withdrawn 4.3 mm isolation figure.
- The 10.4 V rail was quoted as 10.41 / 10.46 / 10.47 V in different places. It is 10.47 V.

### 6. Two things that cannot be fixed now, recorded so they are not re-discovered

- **Silkscreen.** The five boards in fabrication read "10.4V 10s pulse". Cosmetic, not worth
  an engineering query — an EQ would restart PCBWay's lead-time clock for a string. Corrected
  in `gen_pcb.py` so no future revision inherits it.
- **R5 at 77 % of rating.** A 0.25 W 0805 was always a drop-in and the window closed when the
  order went to fabrication. Raising the divider impedance is not available — the divider is
  the LM1117's minimum-load ballast. Note it for a future rev; it is in spec as built.

### 7. On the quote — reviewed and accepted

All 20 lines are priced, no substitutions were taken, and every item the requote asked for
came back. Six lines carry 84 % of the $78.96, and C1 rose 66 % ($1.459 → $2.417) on the
corrected part number despite the requote having been requested on the grounds that it is a
stocked commodity — LCSC lists it near $0.23. At **$22.59 per board** for five prototypes
this does not justify another round trip against a lead-time clock. Recorded in
`pcbway-order-YB1800644.md`, not disputed.

### Correction, same day: item 17 was wrong and is withdrawn

This review opened item 17 — a missed-feed alert in Home Assistant — as "the last
unattended-safety gap". **It already existed, and had since 2026-08-27.** Reading the live
HA config on 2026-09-02 found `automation.reef_tank_feeder_health_watchdog` already
running a 23:45 counter-vs-elapsed-feed-times backstop plus a board-offline branch, and
`automation.reef_tank_af4_scheduled_feed` doing considerably more than "press a button":
a return-pump interlock, a 15-second wait for the on-device lockout as pulse confirmation,
and a counter that increments **only** on that confirmation so a lost press cannot log a
phantom feed.

Worth recording rather than quietly deleting, because **it is the same drift running the
other way**. Every other finding in this review is work done in the repo that never reached
reality; this one is work done in reality that never reached the repo. A review that reads
only the documents will invent open items as readily as it misses closed ones. The repo now
describes both automations as they actually are.

**What is genuinely left is item 20, and it is not fixable in HA.** Every mechanism above
confirms *the pulse was sent*; the 0-10 V port is input-only, so nothing confirms *food came
out*. Connecting the link port disables the aF4's own 24-hour schedule, and an
over-temperature fault stops the feeder and never self-clears — in which case the ESP32
pulses, the lockout asserts, the counter increments, and the watchdog stays silent while
the tank goes unfed. A power-monitoring smart plug on the 12 V supply is the only dispense
evidence available short of opening the unit.
